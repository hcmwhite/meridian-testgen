# Results

`summary.csv`, `coverage_totals.csv`, `coverage_valid_only_totals.csv`, and
`coverage_valid_only_per_file.csv` are generated by
[`scripts/build_results_tables.py`](../scripts/build_results_tables.py), one
invocation per canonical run:

```sh
python3 scripts/build_results_tables.py --run-dir results/runs/<stamp>_... \
  --mode Meridian --model "Claude Opus 5" --coverage-label meridian_opus-5
```

## Column semantics

- `tests_created` — test **functions** the generator/agent wrote (from the
  generator's own `testgen_report.json` count for Meridian runs; a source
  scan for RAW runs, which have no such report).
- `tests_executed` — test **cases** pytest actually collected and ran.
  Usually higher than `tests_created` because `pytest.mark.parametrize`
  expands one function into several cases.
- `valid_tests` — cases that passed.
- `valid_test_failures` — cases that failed on `AssertionError` (a candidate
  finding: the test is valid, it disagrees with the code).
- `invalid_tests` — cases that died on any other exception (a defective
  test, not a finding).
- **`valid_tests + valid_test_failures`** is the "valid" total that appears
  as `valid_pass + valid_findings_assertion_fail` in the coverage tables.

## `coverage_totals.csv` vs. `coverage_valid_only_totals.csv` — one measurement and its correction

`coverage_totals.csv` is the uncorrected number: coverage from every
generated test, as if all of them were valid. `coverage_valid_only_totals.csv`
is the **corrected** version of that same number, after removing the invalid
tests from the measurement — this is the number that should be trusted for
"how good is this suite" analysis (see the Validity section of the
repository README).

Because an invalid test still executes some lines before it dies on its
exception, the correction doesn't just subtract that test's own unique
lines — removing it from the run changes `missed` by whatever it happened to
touch before erroring, which isn't a fixed or predictable amount. So the two
files' `missed` values for the same row are two real, separately-measured
numbers, not one derived from the other by arithmetic. Concrete example,
`raw_codex_gpt-5.6-terra`:

| | statements | missed | coverage_pct |
|---|---|---|---|
| `coverage_totals.csv` — uncorrected (all 15 generated tests) | 202 | 72 | 64% |
| `coverage_valid_only_totals.csv` — corrected (11 valid tests, 4 invalid removed) | 202 | 90 | 55% |

Report a `coverage_pct` alongside a `missed` value **only from the same
row of the same file** — mixing `missed` from one file with `coverage_pct`
from the other produces a self-inconsistent cell.

## Reproducing a row yourself

Requires the `rainbow_keys` app at [`../rainbow_keys/`](../rainbow_keys/)
(included in this repository) and a Python ≥ 3.10 environment with `pytest`,
`coverage`, and `numpy` (see the repository README's reproduction section).
Then:

```sh
python3 scripts/build_results_tables.py \
  --run-dir results/runs/<stamp>_rainbow_keys_... \
  --mode Meridian --model "Claude Opus 5" --coverage-label meridian_opus-5 \
  --codebase rainbow_keys
```

appends one row to each of the four CSVs. To rebuild everything from a clean
slate: delete `coverage_totals.csv`, `coverage_valid_only_totals.csv`,
`coverage_valid_only_per_file.csv`, reset `summary.csv` to its header line,
then rerun the command once per canonical run dir listed in the table above.
